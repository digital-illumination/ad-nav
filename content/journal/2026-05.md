# Journal — May 2026

## 2026-05-10T18:19Z — Claude Code

**Summary:** Adam built and shipped the auth-token injection wrapper for Carson's n8n dispatch, completing the top priority on the Downton next-steps queue. Carson's only outbound HTTP tool is now a single intent-shaped MCP tool whose backing wrapper reads the webhook token from the macOS login Keychain at startup, so the token never enters Carson's prompt context. The work surfaced several real-world gotchas around macOS Keychain access under launchd vs non-interactive SSH, and resulted in three commits on a feature branch ready for merge.

**Decisions:**
- Chose a single-purpose MCP server name (mcp.servers.dispatch + tool 'intent') over a broader n8n server umbrella. Reasoning: dispatch is one operation with one secret scope; future n8n tools would need a separate auth boundary anyway. The principle of one purpose per artifact won out over the slight readability gain of a broader namespace.
- Picked macOS Keychain (with the -A any-app-read flag) over plaintext-in-openclaw.json for the n8n webhook token. The cleaner option of resolving from Bitwarden on every boot would have required pulling the deferred Bitwarden unlock automation forward; the Keychain copy delivers the actual security benefit (token not co-located with the other plaintext secrets in openclaw.json) without that dependency.
- Validation policy at the wrapper is required-field presence only. Schema, type, and business-rule validation stay in the n8n receiver workflow as the single source of truth. Avoids drift between two validators.
- Conservative deployment: kept the old fetch-based HTTP-out alongside the new dispatch path through the first gateway restart, only stripping fetch once dispatch was proven end-to-end via Telegram. Two restarts instead of one, but no point at which Carson lost outbound capability.
